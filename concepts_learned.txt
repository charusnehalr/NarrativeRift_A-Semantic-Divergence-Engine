Semantic Divergence Engine — Concepts Learned
==============================================

1. Propositional Chunking
--------------------------
What: Breaking a document into atomic, self-contained factual sentences (one claim each).
      Unlike semantic chunking (splits by token/sentence count), this extracts meaning-units
      that can stand alone without context — pronouns replaced with proper names.
Where used: src/chunker.py — Gemini extracts propositions from each article.
            Output stored in data/topic_a/propositions/props_{article_id}.json

3. BGE-M3 Embeddings
---------------------
What: A multilingual embedding model by BAAI that produces dense vectors (1024-dim).
      Converts text into a list of numbers that capture semantic meaning — similar meaning
      = similar numbers. Used to find propositions that talk about the same thing across
      different articles, even if worded differently.

Why good here:
  - Multilingual — handles articles from RT (Russian framing), Al Jazeera (Arabic context),
    SCMP (Chinese perspective) that may use different vocabulary for the same event
  - Dense vectors work well with ChromaDB's cosine similarity search
  - Strong performance on short factual sentences (propositions are short)

Where to use:
  - Semantic similarity search across documents
  - Finding paraphrases or related claims from different sources
  - Any task where meaning matters more than exact words

Where NOT to use:
  - Exact keyword search (use BM25/full-text search instead)
  - When you need explainability (vectors are black boxes)
  - Real-time applications on CPU with many documents — BGE-M3 is ~4GB RAM and slow on CPU

Where used: src/embedder.py — embeds all propositions, returns list[list[float]] for ChromaDB
            src/vector_store.py — uses embed_single() to embed query text before similarity search


4. ChromaDB
------------
What: A local vector database that stores embeddings and lets you query by similarity.
      Think of it like a regular database, but instead of searching by exact value,
      you search by "closest meaning" using cosine similarity on the stored vectors.

Why good here:
  - Zero setup — runs locally, no server, no Docker, just a folder on disk
  - Persists to disk (PersistentClient) so embeddings survive restarts
  - Supports metadata filtering (e.g. query only propositions from a specific source)
  - Free, open source

Key rules learned (gotchas):
  - hnsw:space must be set to "cosine" at collection creation — cannot change later
  - All metadata values must be flat scalars (str/int/float/bool) — no lists or dicts
  - On Windows, paths must use forward slashes (Path.as_posix()) — backslashes break SQLite
  - Two separate PersistentClient instances for topic_a and topic_b — never share clients
  - Use upsert (not add) so re-runs are idempotent (safe to run twice)

Where to use:
  - Local similarity search without needing a cloud service
  - Prototypes and portfolio projects where simplicity matters

Where NOT to use:
  - Production at scale (millions of vectors) — use Pinecone, Weaviate, or Qdrant instead
  - When you need distributed/multi-node search

How querying works (why you get text back, not numbers):
  ChromaDB stores BOTH the vector AND the original text together on upsert:
    collection.upsert(embeddings=[...], documents=["original text"], ...)
  When you query:
    1. Your query text is embedded into a 1024-dim vector
    2. ChromaDB compares it against all stored vectors using cosine similarity
    3. It returns the top-K closest matches
    4. For each match it returns the stored "documents" (original text) + metadata
  The text is never decoded from the vector — that is mathematically impossible.
  The vector is only used for FINDING the match. The text was stored alongside it.

  Query flow:
    "ceasefire negotiations" → [0.12, -0.34, ...] → compare → top-5 matches
                                                               → return original sentences + scores

Where used: src/vector_store.py — stores all proposition embeddings, queried during
            contradiction detection to find similar propositions across articles


5. Two-Tier NLI (Natural Language Inference)
---------------------------------------------
What: A pipeline that classifies the relationship between two text propositions.
      Labels: contradiction, entailment (agreement), neutral.
      "Two-tier" means a fast local model handles clear cases, and an LLM handles
      ambiguous ones — saving API quota while maintaining quality.

Tier 1 — DeBERTa (cross-encoder/nli-deberta-v3-base):
  - Local model, runs on CPU, no API calls
  - Takes a pair of sentences → outputs 3 raw logits → softmax → probabilities
  - Label order: [contradiction, entailment, neutral] (index 0, 1, 2)
  - Returns contradiction score 0.0–1.0
  - Score > 0.85 → accept | Score < 0.4 → reject | 0.4–0.85 → Groq

Tier 2 — Groq (llama-3.1-8b-instant):
  - LLM hosted on Groq's hardware, free tier (14,400 RPD)
  - Receives borderline pairs in batches of 5 per API call
  - Returns verdict: CONTRADICTS / AGREES / NUANCE / TEMPORAL / UNRELATED
  - Filters temporal (same event, different time) and nuance (framing, not fact)
  - Only CONTRADICTS verdict adds to final output

Why two-tier:
  - DeBERTa is fast and free but has no understanding of time/context
  - Groq/LLM is slower but understands "Sunday vs Friday = same event, not contradiction"
  - Running LLM on all pairs would be slow and hit rate limits
  - Running only DeBERTa misses temporal/nuance false positives

6. Cross-Encoder Reranker (ms-marco-MiniLM-L-6-v2)
----------------------------------------------------
What: A model that scores relevance between a query and candidate text.
      Unlike bi-encoders (BGE-M3 which embeds separately), cross-encoders
      see BOTH texts at once → more accurate relevance score.

Why used here:
  - ChromaDB returns top-10 by cosine similarity (fast but approximate)
  - Reranker re-scores these 10 candidates more precisely → keeps top-5
  - Prunes irrelevant candidates before expensive DeBERTa NLI calls
  - NOTE: reranker scores relevance, NOT contradiction — it's a pre-filter only

Where NOT to use:
  - First-pass retrieval over large corpora (too slow — use bi-encoder first)
  - When you need embeddings (cross-encoders don't produce vectors)

Where used: src/nli_engine.py — rerank_candidates() called before DeBERTa

7. Deduplication with frozenset
---------------------------------
What: A frozenset is an immutable, unordered set. Used here to track seen pairs.
      frozenset({A, B}) == frozenset({B, A}) → pair A-B and pair B-A are the same.
Where used: src/nli_engine.py — seen_pairs set prevents scoring the same pair twice
            since proposition A querying B and proposition B querying A would
            both return the same pair without deduplication.

8. Graph-Based Contradiction Representation
-------------------------------------------
What: Contradiction pairs are stored as a network graph where propositions are nodes
      and contradictions are edges. This lets you see patterns across many sources
      at once — which outlets cluster together, which claims are most disputed, etc.

NetworkX:
  - Python library for building and analysing graphs
  - Undirected graph (G.add_node, G.add_edge) — direction doesn't matter for contradictions
  - Node/edge attributes store all metadata (text, source, confidence, reasoning)
  - Used here to build the graph structure before handing off to PyVis for rendering

Louvain Community Detection:
  - Algorithm that groups nodes into "communities" — clusters of closely connected nodes
  - In this context: a community = a set of propositions that all contradict each other
    around the same claim (e.g. all disagreements about Russian troop count)
  - Resolution parameter (config: LOUVAIN_RESOLUTION=1.0) controls cluster granularity:
    < 1.0 = fewer, bigger clusters | > 1.0 = more, smaller clusters
  - Output: dict mapping each node → community_id (integer)

PyVis:
  - Wraps NetworkX graphs into interactive HTML using vis.js under the hood
  - Node size = degree (how many contradictions a proposition is involved in)
  - Node colour = news source (so you can see which outlet each claim is from)
  - Edge label = confidence score (0.0–1.0)
  - Edge shade = darker red = higher confidence contradiction
  - Hover tooltip = full proposition text + source + date + Groq reasoning
  - Output is a self-contained HTML file — open in any browser, no server needed

Where NOT to use PyVis:
  - Production dashboards (use D3.js or Plotly instead — more control)
  - Graphs with thousands of nodes (PyVis is slow above ~500 nodes)

2. Lazy Singleton Pattern
--------------------------
What: A module-level variable initialized to None, loaded only on first use, then reused.
      Avoids loading heavy models at import time. Fails at the right time (when actually called).
Where used: src/chunker.py — _gemini_model = None, loaded in _get_gemini_model()
            src/embedder.py — _bge_model = None, loaded in load_bge_model()
            src/nli_engine.py — reranker and DeBERTa models use the same pattern
